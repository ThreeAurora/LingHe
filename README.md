# 灵鹤 LingHe —— 外挂式 AI 中文输入法（小鹤音形向）

外挂模式：免安装、免签名、免驱动。整个文件夹拷到任何位置，`python linghe.py` 即用。

## 为什么是外挂而不是安装式

安装式 TSF 输入法需要注册 DLL、测试签名/证书、随系统更新维护兼容性；外挂只需
一个低级键盘钩子 + 自绘候选窗 + Unicode 注入上屏，单目录绿色运行，改代码即改
输入法。对自用工具而言外挂是明显更省事的路线。

## 快速开始

1. **码表**：把 `简单鹤V9.3.0.txt`（或任何 `词条<TAB>编码` 格式的码表）放进
   `mabiao/` 文件夹即可，无需注册。辅助码表（`*辅助*.txt`）同样放这里，自动加载。
   没有码表也能跑（纯底库 + AI 模式）。
   兜底词库默认已在 `dicts/`（152 万词，雾凇拼音），想换就替换该文件夹内容。
2. **AI**（可选但推荐，决定体验上限）：
   - 本机跑着 Ollama（11434）或 LM Studio（1234）→ 自动探测接入，无需配置；
   - 想用云端/其他端点 → 改 `config.json` 的 `ai.api_base / api_key / model`。
3. 运行（任选其一）：

```bat
run.bat                                        -- 双击启动（已配好本机 Python 路径）
E:\miniconda3\python.exe linghe.py             -- 前台运行，看日志
E:\miniconda3\python.exe linghe.py --smoke     -- 自检（码表/钩子/AI 探测），不常驻
```

> 注意：需要带 tkinter 的 Python（miniconda 自带；嵌入式发行版没有）。零第三方依赖。

4. 打字：
   - 正常敲小鹤音形码，已背熟的字按码表固频出现在候选前部（通常就是首选）；
   - 没背过的字/词，AI 顺延在码表命中之后（码表命中 k 个，AI 从第 k+1 位起）；
   - 码表无命中时 AI 候选直接顶到首选（候选窗短暂显示 … = AI 思考中）。
   - `空格`或`1`=上屏首选；`;`=2选；`'`=3选；`1~9`=选字；`退格`=删码；`Esc`=清码；`组码中按标点`=上屏首选后标点照常；
   - `回车`=上屏已敲的英文字母本身（打英文单词不用先切英文）；
   - `Shift 单击`（400ms 内按下抬起）：**组码中=上屏已敲的英文**；空码时=中/英全局切换（闪 `[中]`/`[EN]`）。
     **英文模式=纯英文直通**：字母/数字/标点全透传，无候选窗、无组码、无任何 UI，打英文如同没开输入法；
   - `=`/`Tab`=候选下一页（末页回卷），`-`=上一页；候选池 45 个分页显示；
   - `Ctrl+Alt+L`=暂停/恢复外挂。
   - **无长度上限**：第 5 码起继续当纯双拼音节（不会自动上屏四码），六码可打
     「詹姆斯」（vjmusi），更长的整句走声母简拼（见下文「简拼」）。

## AI 运行时（ai_runtime/）

`run.bat` 会自动：
1. 检测 11434 端口，没在跑就启动 Ollama serve（优先 `ai_runtime/ollama/` 便携版，
   否则用官方安装版），**当前强制 CPU 模式**（本机 RTX 2060 驱动栈异常：
   `nvidia-smi` NVML 初始化失败、CUDA 推理 500 卡死；驱动修复后删除 run.bat 里的
   `CUDA_VISIBLE_DEVICES=-1` 一行即可回到 GPU）；
2. 启动灵鹤本体。

实测（qwen2.5:1.5b，CPU 8 线程）：首次加载 ~25s，热调用 **0.22~0.3s**
（`OLLAMA_KEEP_ALIVE=-1` 模型常驻不卸载，不会因超时被踢出显存/内存再冷启动），
输入法异步预测体感无卡顿。

想换更强模型（驱动修好后推荐）：`ollama pull qwen2.5:3b`（或 7b，GPU 上 <1s），
改 `config.json` 的 `ai.model`；端点探测在指定模型不存在时自动回退第一个可用模型。
用云端 API：清空 `ai.model`，填 `api_base / api_key`（OpenAI 兼容格式）。

**注意**：模型放官方默认位置（`C:\Users\<你>\.ollama\models`）时不要设置
`OLLAMA_MODELS` 环境变量，官方版 serve 才找得到。

## 候选排序公式（核心约定）

```
候选池（45 个，分页显示）
  = [ 辅助码筛选命中 ]            ← 最高优先，直接顶到首选（作用于码表+底库全部词）
  ++ [ 码表侧(固频序) 精确码 + 前缀命中 ]   ← 主码表固定调频，永不重排
  ++ [ 底库词（动态调频：统计重排）]
  ++ [ Viterbi 整句切分（第 5 码起，全拼/简拼两路按每字代价合并）]
  ++ [ AI 预测（仅长码异步补位）]
```

**码表是固频的（背熟的字按码表行序，永不重排）；底库是动态调频的**——统计重排
只作用于底库候选。重排模型：`词频(unigram, 底库真实词频) + 用户个性化(上屏次数)
+ 长词奖励/单字惩罚 + 上文 bigram(在线学习)`，参数由 `tune.py` 在真实用例上扫参
定案（L=12/P=4，全拼整句 10 例命中 9）。

静态侧（码表前缀索引 + 底库双索引）实测码表 0.005~0.04ms、底库亚毫秒——
「0.1 秒出词」由它们保证；整句切分（Viterbi beam）单次 1~3ms 本地出整句；
AI 只在第 5 码起异步补位（生成式 LLM 物理上进不了打字节奏，整句场景有天然
停顿才用得上它），config 里 `ai.enabled=false` 可整体停用。

## 辅助码（手心辅助码）

把 `*辅助*.txt`（如 `简单鹤V9.3.0电脑手心辅助码.txt`）和码表一起放进 `mabiao/`，
自动加载（实测 9980 行，覆盖 8400 字）。**只用首键**筛选（主人明确要求不用第二码）。

一个键串会被 `parser.py` 同时按三种确定形态解析，命中即并集输出：

| 形态 | 触发 | 例 |
|---|---|---|
| 纯音节 | 偶数长 | `yiyi` → 意义/异议… |
| 词尾单辅助码 | 奇数长（≥3） | `yiyit` → 异议（t=异的辅码，表「任意字」） |
| 全辅助码 6 码 | 长度 3 的倍数 | `yityic` → 异议（t=异，c=议，逐字定位） |

规则要点：辅助码只能加在**词尾**，或**每个字都加**（凑成 6 码）；不允许中间穿插
半个（`yityi` 这种是错的）。筛选后仍有多个候选时，按码表原顺序（固频）排列。
打词时**任意**一个字的辅助码都能把该词筛到首选。

## 兜底底库（dicts/）

码表之下挂了一个大词库作为底座，来源 GitHub 开源项目 **rime-ice/雾凇拼音**：

| 文件 | 词条 | 说明 |
|---|---|---|
| `base.dict.yaml` | 543092 | 通用词库，自带拼音 |
| `tencent.dict.yaml` | 980968 | 三字以上词/网络流行语，**无拼音**，靠 `char_pinyin.txt` 逐字自动注音 |
| `char_pinyin.txt` | 44437 | 汉字→拼音全表（mozillazg/pinyin-data，jsDelivr 镜像） |

合计 **1521598 词条**，后台线程异步加载（约 15s，期间输入法已可用，加载完闪
`[底库就绪 N词]`）。双索引：全拼 `zhan mu si`→詹姆斯、声母简拼 `u v u`→深圳市。
查询实测 0.002ms。

**自动记忆**：每次上屏都会把「词 + 拼音」写入 `dicts/user_dict.txt`（词频累加），
下次起该词按使用次数优先出现。新词/网络词打过一次就记住，无需手工加词。
同时学习相邻词共现（`dicts/user_bigram.txt`），重排与整句切分随使用越来越准。
退出时自动落盘（每 30 次上屏批量合并写一次，不碰击键路径）。

底库首次加载做一次性文本解析（约 22s，后台线程不阻塞），之后走 marshal 二进制
缓存（`dicts/.cache.bin`，按词库文件签名自动失效）数秒内就绪。

## 简拼（整句声母）

第 5 码起若不是规整双拼，就当**整句声母简拼**处理：每键取一个字的声母
（zh/ch/sh 记作 v/i/u）。例如 `wilygbz` → 我吃了一个包子。

这条路径由三层共同承担（由快到慢）：
1. **底库简拼索引**：声母串恰是整词的（如 `u v u`→深圳市），0.002ms 即时命中；
2. **Viterbi 统计整句切分**：把声母/音节流切成词序列，本地 1~3ms 出整句
   （全拼整句 10 例命中 9：我吃了一个包子/今天天气不错/我们一起去吃饭…）。
   简拼冷启动受 unigram 歧义限制（wilygbz 暂出次优解），但**越用越准**——
   上屏自动学习 bigram 共现（`dicts/user_bigram.txt`），打过一次下次就对；
3. **AI 异步精修**：整句场景有天然停顿（打完一串键才看结果），AI 数百 ms
   的结果能赶上，按（上下文+键码）缓存。

`xiaohe.interpret()` 对 >4 码同时给出「多音节词」和「整句声母简拼」两种解读，
AI 提示词带 few-shot 示例，实测 `wilygbz → 我吃了一个包子`（305ms）。

## 关于「0.1 秒内 AI 调频」：豆包是怎么做到的

先说结论：**LLM 生成式推理做不到，API 只会更慢。** 这不是工程优化问题，是物理限制。

- 自回归生成必须逐 token 串行解码，1.5B 模型 CPU 上热调用也要 0.22~0.3s；
- 走 API 还要叠加网络 RTT（本机到云端 20~80ms 起步）+ 排队 + 更长的前缀处理，
  实测必然慢于本地；**API 的价值是模型更强（准），不是更快**。

豆包输入法那种「明显有 AI 又 <0.1s」的真实架构是**双层**：

```
第一层（<1ms）：   Trie/词表候选生成 —— 拼音切分、词典召回，产出 50~200 个候选
                   ↑ 这一层保证「0.1 秒出词」，本质是检索不是生成
第二层（5~30ms）： 端侧判别式重排模型（小 BERT / 双塔，几十 MB）
                   —— 输入 (上下文, 候选) 打分，只做一次前向传播，不生成 token
                   ↑ 这一层提供「太智能了刚好是我要的词」的体感
```

关键差异：重排是**判别**（对已有候选打分，一次前向，可批处理、可端侧跑），
生成是**自回归**（必须一个字一个字吐，串行不可并行）。所以「AI 调频」的
正确姿势是「检索召回 + 判别式重排」，而不是「让 LLM 当场造句」。

灵鹤当前的对应实现与差距：
- 第一层已具备（码表前缀索引 + 底库双索引，共 170 万级词条，<0.04ms）；
- 第二层目前用生成式 LLM 异步补位（准但不快，且只补静态侧没打满的空位）；
- **下一步**：训练/接入一个小判别式重排模型（几十 MB 的 BERT 双塔），对上下文+
  候选打分做真正的 <100ms 调频；届时 LLM 退居「生僻长句兜底」。这是唯一能同时
  满足「0.1s」和「明显有 AI」的路线。

## AI 预测

- 每次组码异步发起预测（只保留最新请求，继续打字自动作废旧请求，不卡手）；
- 上下文 = 本外挂自己上屏的历史文本（切窗口自动清空），连同键入码的拼音解读
  （4 码给「单字音形」+「二字词」两种解读；>4 码给「多音节词」+「整句声母简拼」）
  一起喂给模型；
- 模型只要求输出 JSON 候选数组；结果按（上下文+键码）缓存；
- AI 未就绪/超时时自动降级为纯码表模式，按键永不阻塞。

## 目录结构

```
linghe.py        主引擎：键盘钩子、组码状态机、候选装配、翻页、上屏
ai_engine.py     AI 端点探测 + 异步预测 + 缓存（仅长码补位，可停用）
mabiao.py        码表加载（词条<TAB>编码 + 前缀索引，固频）
parser.py        多假设码串解析器（纯音节/词尾辅码/全辅码 6 码）
fuma.py          手心辅助码（只取首键）加载与匹配
dict_engine.py   兜底底库：全拼/简拼双索引 + 自动记忆 + marshal 缓存
rerank.py        端侧统计重排器 + Viterbi 整句切分（豆包第二层）
tune.py          重排参数调优器（改 rerank 常数前必跑）
xiaohe.py        小鹤双拼键位与拼音解读
candidate_ui.py  候选窗（分页显示）
config.json      配置（ai.enabled / candidate_pool 等）
mabiao/          码表文件夹（码表 + *辅助*.txt，放这里就能用）
dicts/           兜底词库文件夹（8105字表/base/tencent + char_pinyin + 用户词/共现）
ai_runtime/      便携 Ollama + 模型库（run.bat 自动管理）
```

## 已知限制

- 管理员权限窗口里钩子失效（UIPI 限制），需要时以管理员身份运行本程序；
- 上屏用 Unicode 注入，对极少数 DirectInput 游戏/密码控件无效；
- 候选窗跟随光标（UI caret），个别自绘光标应用回退到鼠标位置；
- 无托盘图标（后续加）；UI 是刻意简陋的（主人说了 UI 随意，后面再说）；
- 底库首次加载约 15s（后台线程，不阻塞，期间输入法已可用）；
- LLM 只做异步补位，不做同步调频——真正的 <0.1s 调频需接判别式重排模型（见上）。

## 路线图（后面再说）

- **判别式重排模型**（小 BERT 双塔，端侧 5~30ms）—— 通往「豆包级智能调频」的
  唯一路线，也是当前最大的体验差距所在；
- 托盘常驻 / UIA 读取目标应用上文增强上下文 / 候选窗美化 /
  学习用户选字频次微调 AI 提示 / 打包单 exe。
